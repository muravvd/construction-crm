# СтройCRM — объекты и задачи

Мини-CRM для строительной компании: постановщики ведут объекты (стройки) и задачи, исполнители берут задачи в работу и отдают на проверку.

- **Приложение:** _ссылка на Netlify_
- **Стек:** React 19 + TypeScript, Vite, Ant Design, Supabase (PostgreSQL, Auth, RLS)
- [Объяснение для руководителя](docs/EXPLANATION.md)
- [Решения и допущения](docs/DECISIONS.md)

Для проверки разграничения прав: у первого исполнителя задачи на двух объектах, у второго — на всех трёх. Поэтому «Склад на Промышленной» первый исполнитель не видит.

## Как устроено

Отдельного сервера нет. Браузер обращается напрямую к Supabase с публичным ключом, а все права проверяет сама база данных:

- **GRANT** определяет, что вообще можно делать с таблицей. Например, у задачи через API нельзя записать поля `status`, `author_id` и `created_at`, а историю статусов можно только читать.
- **RLS** (Row Level Security) определяет, какие строки видны и изменяемы. Исполнитель видит только задачи, где он назначен, историю этих задач и объекты, в которых у него есть задачи. Создавать, менять и удалять объекты и задачи может только постановщик.
- **`change_task_status()`** — единственный способ сменить статус. Функция проверяет роль, исполнителя задачи, допустимость перехода и комментарий, а затем записывает историю.
- **Триггеры** запрещают менять статус в обход функции, ставить исполнителем не-исполнителя и изменять записи истории (даже администратору в SQL Editor).

Весь SQL лежит в [`supabase/migrations/0001_schema.sql`](supabase/migrations/0001_schema.sql), тестовые данные — в [`supabase/seed.sql`](supabase/seed.sql).

Структура фронтенда:

```
src/
  lib/        supabase-клиент, запросы к API, типы, статусы и доступные действия
  auth/       сессия и профиль пользователя, защита страниц
  components/ таблица задач, формы, кнопки смены статуса, история
  pages/      вход, объекты, карточка объекта, задачи, карточка задачи
```

## Запуск с нуля

Нужен Node.js 20+ и бесплатный проект на [supabase.com](https://supabase.com).

### 1. Supabase

1. Создайте проект. В **Authentication → Sign In / Providers** выключите **Allow new users to sign up**.
2. В **SQL Editor** выполните `supabase/migrations/0001_schema.sql`.
3. В **Authentication → Users → Add user → Create new user** создайте пользователей с галочкой **Auto Confirm User**:
   `manager@stroycrm.test`, `executor1@stroycrm.test`, `executor2@stroycrm.test`.
4. В **SQL Editor** выполните `supabase/seed.sql`. Скрипт назначит роли и создаст 3 объекта и 7 задач во всех статусах.

Новых сотрудников добавляют так же через **Add user**. Профиль создаётся автоматически с ролью «исполнитель». Постановщика назначают в SQL Editor:

```sql
update public.profiles set role = 'manager', full_name = 'Имя Фамилия' where id = (select id from auth.users where email = '...');
```

### 2. Приложение локально

```bash
cp .env.example .env.local   # вписать Project URL и Publishable key из Project Settings → API Keys
npm install
npm run dev                  # http://localhost:5173
```

### 3. Проверка безопасности

Локально, без Supabase: схема и тестовые данные прогоняются во встроенном PostgreSQL с проверками прав для каждой роли.

```bash
npm run test:db
```

На настоящем Supabase скрипт входит под исполнителем и постановщиком и пытается сделать запрещённое прямыми запросами к Supabase, в обход интерфейса: читать чужие задачи, менять статус напрямую, подделывать историю, назначать себя постановщиком и т.п. Все попытки должны быть отклонены.

```bash
cp .env.test.example .env.test.local   # вписать пароли тестовых пользователей
npm run security-check
```

### 4. Публикация на Netlify

1. **Add new project → Import from Git**, выбрать репозиторий. Команда сборки и папка берутся из `netlify.toml`.
2. В **Site configuration → Environment variables** добавить `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
3. Deploy.

## Ключи

Во фронтенде используется только **publishable key**. Он публичный по своей природе: без входа по нему ничего не доступно, а после входа действуют правила базы. Ключ `service_role` / secret не используется нигде в проекте. Файлы `.env.local` и `.env.test.local` исключены из git.
