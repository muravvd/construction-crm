# Решения и допущения

## Роли и пользователи

- **Роль хранится в таблице `profiles`, а не в метаданных пользователя Supabase.** Пользователь может сам менять свои `user_metadata` и назначил бы себя постановщиком. Изменять `profiles` через API не может никто.
- **Роль одна на пользователя.** Постановщик не может быть исполнителем, исполнителем задачи может быть только пользователь с ролью «исполнитель» (проверяется в базе).
- **Новые пользователи получают роль «исполнитель».** Профиль создаётся триггером при создании пользователя в Supabase Auth. Постановщика назначают вручную через SQL Editor, интерфейса управления пользователями нет.
- **Имена и роли всех сотрудников видны всем вошедшим.** Без этого исполнитель не увидел бы, кто автор задачи и кто менял статус. Email, пароли и прочие данные учётных записей не видны.
- **Удалить сотрудника, у которого есть задачи или записи истории, нельзя:** база не даст, чтобы не потерять историю. Отключить доступ можно блокировкой пользователя в Supabase Auth.

## Задачи и статусы

- **Исполнитель обязателен** при создании задачи. ТЗ говорит «назначает исполнителя», а задача без исполнителя никому не видна, кроме постановщиков, и не может двигаться по статусам.
- **Постановщик может редактировать название, описание, объект и исполнителя в любом статусе**, в том числе переназначить задачу «в работе» на другого исполнителя. Бывший исполнитель после этого перестаёт её видеть, новый видит её вместе со всей историей.
- **Статус нельзя отредактировать как обычное поле.** Он меняется только функцией `change_task_status` и только по разрешённым переходам. Постановщик тоже не может, например, сразу принять «новую» задачу: в ТЗ таких переходов нет.
- **Любой постановщик может принимать или возвращать любую задачу**, не только свою. ТЗ говорит, что постановщиков может быть несколько и они «видят всё».
- **Комментарий можно оставить при любой смене статуса**, обязателен он только при возврате на доработку.
- **Создание задачи — первая запись в истории** («Задача создана», статус «Новая»), чтобы было видно, кто и когда её поставил.
- **Для исполнителя чужая задача неотличима от несуществующей:** сообщение «Задача не найдена», без подтверждения, что такая задача есть.

## Объекты

- **Исполнитель видит объект, пока у него есть в нём хотя бы одна задача, в любом статусе, включая «Принята».** В карточке объекта он видит только свои задачи.
- **Удаление объекта удаляет все его задачи вместе с историей; удаление задачи удаляет её историю.** Интерфейс предупреждает об этом. История неизменяема и не удаляется отдельно, но она часть задачи, а удалять задачи ТЗ разрешает постановщику. Альтернатива — «архив» вместо удаления (см. ниже).

## Безопасность — что сделано сверх минимума

- **Права на таблицы выдаются явно, независимо от настроек проекта.** Схема сначала отбирает все права у `anon` и `authenticated` (на случай, если включено «Automatically expose new tables»), затем выдаёт нужные явными `GRANT` только роли `authenticated`. У анонимного пользователя нет доступа ни к чему.
- **Права на запись выданы по колонкам:** через API у задачи нельзя записать `status`, `author_id`, `created_at` ни при создании, ни при изменении. Автор и дата ставятся базой.
- **Служебные функции лежат в схеме `private`**, которая не опубликована через API.
- **Записи истории нельзя изменить даже администратору в SQL Editor** (триггер).
- **Проверки на двух уровнях.** `npm run test:db` прогоняет схему и тестовые данные во встроенном PostgreSQL (PGlite) и выполняет 37 проверок прав: что разрешено и что должно быть отклонено. `npm run security-check` проверяет настоящий Supabase прямыми запросами в обход интерфейса.

## Что не сделано / можно улучшить

- Архивирование объектов и задач вместо физического удаления.
- Управление пользователями и ролями из интерфейса. Потребует серверной функции с секретным ключом (Supabase Edge Function).
- Пагинация и поиск на сервере. Сейчас списки загружаются целиком, для десятков объектов и сотен задач это нормально.
- Сгенерированные типы базы данных (`supabase gen types`). Сейчас типы описаны вручную в `src/lib/types.ts`.
- Обновление данных в реальном времени (Supabase Realtime). Сейчас изменения других пользователей видны после перехода по страницам.
- Сброс пароля по email. Сейчас пароли задаёт администратор.
- Автотесты интерфейса.
